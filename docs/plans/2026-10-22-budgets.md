# Budgets (first slice)

Build order step after rules (docs/konzept.md, "Kernkonzepte & Datenmodell" (Budget),
"Familienfunktionen", "Dashboard & Kennzahlen" (Budgets, Budgetverbrauch), "Kategorien &
Sonderfälle" (Erstattung)).

## Goal

On the account page (`/accounts/[id]`) members see a budgets section for the selected month: one
progress bar per budget ("Lebensmittel 312,40 € von 400,00 €"), warning colour from 80 %, error
colour over 100 %. A small form adds a budget (category and monthly limit), changes its limit and
deletes it.

A budget belongs to one account and one expense category (a group like `groceries` covers its
subcategories, or a single subcategory like `groceries.supermarket`) and has a monthly limit in
integer cents. Months are calendar months. One budget per account and category.

Spending of a budget in a month = the expenses of that account in that category (group: also its
subcategories) in that month. Refunds booked as positive expenses lower the spending (concept:
"Erstattung verringert die Ausgabe der ursprünglichen Kategorie"). Transfers, saving and income
never count. Expenses without category count for no budget.

Privacy: a budget is visible and editable for whoever may see its account; budgets of a private
account only for its owner. If a shared account becomes private, its budgets disappear for the
others.

Out of scope (later slices): dashboard and "Alle meine Konten" view, budget suggestions from average
spending, copying budgets to other accounts, notifications, budgets for income categories.

## Decisions

- **Budgets get their own part, `src/budgets`** (uses shared, transactions), as CLAUDE.md lists it.
  It owns the `budget` table, its service, the budgets section and its texts.
- **How budgets reads spending: one new function on the existing transactions object**,
  `transactions.expenseTotals(tx, accountId, month?)`. It runs inside budgets' database transaction
  (like `findBookings` for rules) and returns `{ month, totals }`: the net sum of the account's
  expenses per category key in that calendar month (missing month = current month, using transactions'
  own month helpers). transactions keeps the knowledge of what an expense is and which dates belong to
  a month; budgets only adds up the keys of a budget (`groceries` = `groceries` + `groceries.*`).
  This needs no new export, no new SQL contract and no migration in transactions. Alternative
  rejected: a SQL function owned by transactions (one more migration and contract, nothing gained).
- **Account access via accounts' SQL function `accounts_visible_account_ids()`**, as transactions
  does, in the service and in row-level security. No new edge to accounts.
- **Only the limit can be changed.** Changing the category is "delete and add"; it keeps the form
  small and avoids a second duplicate check.
- **Duplicate** (same account and category) is rejected with `duplicate` (409), backed by a unique
  index.
- **One migration file.** `0019_budgets.sql` is generated by drizzle-kit; the foreign key, grants and
  row-level security are appended to the same file (earlier parts used a second, custom migration;
  one file keeps this slice small).
- **Progress** is computed on the server: `spentCents` (may be below 0 if refunds exceed expenses),
  `limitCents`. The bar shows `max(0, spent) / limit`; ≥ 80 % `progress-warning`, > 100 %
  `progress-error`, else `progress-success`.

## Privacy design (for sign-off)

1. **Row-level security on `budget`** (SELECT, INSERT, UPDATE, DELETE):
   `account_id IN (SELECT accounts_visible_account_ids())`; INSERT also
   `created_by_user_id = auth_current_user_id()`. GRANT SELECT, INSERT, UPDATE, DELETE to app_user.
2. **The service runs in the caller's session** (`withSession`) and checks the account with the same
   function; spending is read through transactions in the same session, so transactions' RLS applies
   too.
3. API and page: a budget or account the caller may not see gets the same 404 as an unknown id.
   Budget views carry no user ids.

## Design

### 1. Data model

`budget` (src/budgets/schema.ts, code name `budget`, owner: budgets)

| column | type | notes |
| --- | --- | --- |
| id | text pk | |
| account_id | text not null | FK to `account` ON DELETE CASCADE (appended SQL) |
| category | text not null | expense category key (group or subcategory) |
| limit_cents | bigint not null | check > 0 |
| created_by_user_id | text not null | |
| created_at, updated_at | timestamp | |

Unique index `(account_id, category)`.

### 2. transactions change

- `expenseTotals(tx, accountId, month?) → { month, totals: Record<string, number> }`: visible
  bookings of kind `expense` with a category, in the month's date range, `sum(amount_cents)` grouped
  by category (negative = money spent, positive refunds lower it).

### 3. budgets part (src/budgets)

- `validation.ts` (browser-safe, Zod, messages are keys `budgets.validation.*`):
  `createBudgetSchema` (`accountId`, `category` – must be an expense category via transactions'
  `isCategoryFor`, `limit` – German amount > 0), `updateBudgetSchema` (`limit`), `monthSchema`.
- `create-budgets.ts`: `createBudgets({ db, transactions })`, every call in `withSession`:
  - `listBudgets(caller, accountId, month?)` → `{ ok, month, budgets: BudgetView[] }` or
    `not-found` / `invalid-input`. `BudgetView`: id, accountId, category, limitCents, spentCents.
    Sorted by category key.
  - `createBudget(caller, input)` → `ok` / `invalid-input` / `not-found` / `duplicate`.
  - `updateBudget(caller, id, input)` → `ok` / `invalid-input` / `not-found`.
  - `deleteBudget(caller, id)` → boolean.
- `components/budget-section.tsx` (client): title, one row per budget with category name
  (transactions' `useCategoryName`), "312,40 € von 400,00 €", progress bar, edit limit inline,
  delete with confirmation; add form with `CategorySelect` (expense) and amount. Calls the API and
  `router.refresh()`.
- `messages/{de,en}.json`, `messages/index.ts` (namespace `budgets`).

### 4. app (thin)

- `_lib/budgets.ts` (instance), `_lib/budgets-route.ts` (handlers).
- `POST /api/budgets`, `PATCH/DELETE /api/budgets/[id]`. 401 without session, 404 for invisible or
  unknown ids, 400 invalid input, 409 duplicate.
- Account page: loads `budgets.listBudgets(caller, id, month)` and shows `BudgetSection` above the
  bookings (hidden if the month filter is invalid).
- `_lib/i18n/messages.ts` merges `budgetsMessages`; `drizzle.config.ts` lists the schema.

### Logging

No amounts, names or categories in logs or error messages.

2. Schema, drizzle config, migration 0019 (generated, then FK, grants and RLS appended).
3. transactions: `expenseTotals` (TDD).
4. budgets: validation, service with progress, privacy and RLS tests (TDD), section, messages.
5. app: instance, handlers, routes with privacy tests, account page, message merge.
6. CLAUDE.md: budgets line (uses shared, transactions; account access via accounts' SQL function).
7. Browser check; `npm test`, `npx tsc --noEmit`, `npm run lint`.

## Tests

- transactions `expenseTotals`: only expenses with category in the month; refunds (positive
  expenses) lower the total; transfers, saving, income and other months are left out; invisible
  account gives nothing.
- budgets service: group budget covers subcategories, subcategory budget only itself; refund lowers
  spending; transfer/saving/income ignored; month default = current month; duplicate rejected;
  category must be an expense category; limit must be > 0; update changes the limit only; delete.
- Privacy (mandatory, service and routes): Erika never sees budgets of Max's private account (list →
  not-found), her PATCH/DELETE on them → 404 like unknown ids, data unchanged; she cannot create a
  budget on his private account (404); budgets on a shared account are visible and editable for both;
  they disappear for Erika when Max makes the account private; another household sees nothing; 401
  without session.
- RLS: `budget` rows of invisible accounts not readable or writable; insert with another creator
  fails.
- Messages: de and en have the same keys (existing test).
